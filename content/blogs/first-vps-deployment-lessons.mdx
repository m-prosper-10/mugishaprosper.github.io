Up until this month, "deploying an application" for me meant connecting a GitHub repository to a platform like Vercel, Render, or Railway and watching a green checkmark appear.

Those platforms are great, but once you want to run a backend worker, a PostgreSQL database, a Redis instance, and a small Python service together, the monthly bill scales fast—and worse, you realize you have no idea how your code actually runs on a real server.

So I rented a raw Ubuntu VPS, SSH'd into a blinking root prompt, and decided to deploy my stack myself using Docker and Nginx. I thought it would take two hours on a Saturday morning. I finished on Sunday night.

Here are the three traps I walked straight into that no "Docker in 15 Minutes" video warned me about.

---

## Trap #1: My First Docker Image Was 1.3 Gigabytes

To containerize my Node/TypeScript service, I wrote what I thought was a completely normal `Dockerfile`:

```dockerfile
FROM node:20
WORKDIR /app
COPY . .
RUN npm install
RUN npm run build
CMD ["npm", "start"]
```

It worked on my laptop. Then I tried building and pulling it on a cheap VPS with 1 vCPU and 20GB of disk space. After four deployments, the server ran completely out of disk space and crashed because `/var/lib/docker` was full of gigantic image layers.

Why was a simple REST API producing a `1.3GB` image?
1. `FROM node:20` pulls a full Debian operating system packed with build tools, compilers, and system libraries you never use at runtime.
2. `COPY . .` (without a `.dockerignore` file) copied my local `node_modules` and `.git` folder into the build context.
3. All my `devDependencies`, TypeScript source files, and build caches stayed inside the final image forever.

Learning about **multi-stage builds** and Alpine/slim base images felt like discovering a cheat code. By compiling TypeScript in a build stage and copying *only* the compiled `dist/` folder and production dependencies into `node:20-alpine` running as a non-root user, the image shrank from **`1.3GB` down to `135MB`**.

## Trap #2: Docker Quietly Bypasses `ufw` Firewall Rules

This one genuinely scared me when I discovered it.

To secure my new Ubuntu server, I followed a standard Linux hardening guide: I disabled root password SSH login, enabled `ufw` (Uncomplicated Firewall), and allowed only ports `22` (SSH), `80` (HTTP), and `443` (HTTPS):

```bash
sudo ufw default deny incoming
sudo ufw allow 22/tcp
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
sudo ufw enable
```

Then I started my PostgreSQL container in `docker-compose.yml` with:

```yaml
ports:
  - "5432:5432"
```

I assumed that because `ufw` blocked every incoming port except `22`, `80`, and `443`, port `5432` was only accessible on the server itself, or at least protected by my firewall.

Out of curiosity, I ran `nmap` against my server's public IP address from my laptop. **Port `5432` was wide open to the entire public internet.**

Why? Because when you publish a port with `-p 5432:5432`, Docker manipulates Linux `iptables` directly in the `nat` (`PREROUTING`) chain, which executes *before* `ufw`'s filtering rules ever see the packet!

If a container only needs to talk to other containers on the same host, it doesn't need a `ports:` mapping at all—containers on the same Docker network can already reach each other by service name (`postgres:5432`). And if you *do* need a port exposed on the host for a local reverse proxy, bind it explicitly to loopback:

```yaml
ports:
  - "127.0.0.1:5432:5432"
```

One `127.0.0.1:` prefix is the difference between a private database and thousands of brute-force bots hammering your Postgres instance all night.

## Trap #3: Logs That Eat Your Hard Drive

One last lesson: by default, Docker keeps every line of `stdout` and `stderr` your containers print in a JSON file on disk forever, with no maximum file size limit. If an app logs a stack trace on every request, your disk fills up in a month.

Adding a simple `logging` block to `docker-compose.yml` (or `/etc/docker/daemon.json`) with `max-size: "10m"` and `max-file: "3"` caps log files automatically so a chatty service can never brick the host machine.

PaaS platforms are convenient, and I still use them for static sites. But spending a weekend setting up Nginx, Certbot TLS, `ufw`, and Docker on a raw Linux box taught me more about how the web actually works than six months of writing framework code.
